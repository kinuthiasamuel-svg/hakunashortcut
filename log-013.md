THE FRICTION POINT.

*The Unfiltered Realist*

LOG 011 mapped the switches. LOG 012 mapped what happens when they disagree. Now comes the question that actually changes behavior:

Knowing all of that, what do you build?

Drive on Kenya’s Thika Super Highway, and you already have the answer.

Eight lanes of fast-moving traffic. Flyovers carrying one road clean over another without merging.

Interchanges where routes cross, without becoming the same route, and running the full length of the highway-quieter, slower, rougher, -the service lanes.

The service lane isn’t the main road, it doesn’t move as fast, doesn’t carry the same volume of traffic, but it runs the same direction. It reaches the same destination, and stays open when the highway has a checkpoint, a closure, or a traffic jam.

The tempting answer when a platform switch fires is to leave, find a road with fewer checkpoints, go somewhere the tollbooths are less aggressive. That move misses the point entirely.

The switches aren’t a flaw in one platform, they are a feature of the architecture - payment infrastructure, identity verification, trust systems, access controls.

They exist wherever value moves, you don’t outrun them by switching roads.

The operator who survives the control layer doesn’t find an expressway without checkpoints, they make sure the checkpoint on the expressway can only stop them on that road, -not on the service lane running alongside it. That’s the parallel road.

The parallel road is not necessarily independent infrastructure, it is independent capability.

THE BREAKDOWN.

*The Village Analyst*

THE PLATFORM AS A LANE, NOT THE ROAD.

Most operators build their operation the way a town builds around a single highway, everything flows through one road.

Identity lives on one platform.

Income arrives through one payment processor.

Audience lives on one network.

Work is stored in one cloud service.

Communication runs through one provider.

When the highway is open, everything moves, when a checkpoint appears, suddenly everything stops-not because the checkpoint was meant to control every movement, but because nothing was ever built to move any other way.

The parallel road doesn’t replace the highway. It answers one question:

Which parts of my operation should remain functional even when an external switch changes state?

That question produces a different kind of inventory than “have two accounts on two platforms.”

The right column is sovereign infrastructure, assets that keep functioning even when something in the left column goes dark. None of this requires abandoning the left column.

- The platform still matters. -The payment processor still processes. -The social network still reaches people.

The difference is that none of them gets to be the single point of failure for the entire operation.

THE BLAST RADIUS PRINCIPLE. A resilient operator doesn’t eliminate the switches, they reduce what each switch is capable of switching off.

A switch that fires on one lane should freeze that lane, not the whole road.

That means building so that:

- An identity hold on one platform doesn’t also freeze your payout on another.
- A payment processor restriction doesn’t also kill your ability to invoice directly.
- A social account suspension doesn’t also end your relationship with your audience.
- A cloud outage doesn’t also erase the only copy of three years of work.

Each switch should have a defined blast radius. The operator’s job is to shrink it, before a cascade starts, not after.

FIELD OBSERVATION.

*North Kinangop Dispatch*

The infrastructure sprint that built this archive wasn’t only about publishing, it was an accidental dry run of the parallel road.

Public archive on GitHub.

Private command centre in a separate repository.

Scripts that run locally when cloud pipelines are blocked.

Manual fallbacks documented for every automated step.

When Cloudflare blocked the RSS verification script running from Codespaces, there was a fallback: open the feed directly in a browser.

When the Codespace dropped connection mid-session, the work had already been committed.

When a single-repo architecture turned out to be a security risk, the content survived the restructure because nothing critical lived in only one place.

None of that was planned as infrastructure resilience, it emerged from building deliberately….., one fallback at a time, each one documented before it was needed.

That’s the dry run discipline.

Not a simulation, neither a disaster recovery plan sitting in a folder nobody reads. A series of small builds, each one quietly answering the question: what happens here if this stops working?

THE PLAYBOOK.

*The Stoic Survivor*

Start with the sovereign inventory, not the platform list.

Don’t begin by asking “which platforms am I on?” Begin by asking “which parts of my operation are genuinely mine — regardless of what any platform decides?” Identity records. Intellectual property. Audience relationships. Contact database. Transaction history. Work samples. Operating procedures. Access recovery credentials. That inventory is what you’re building to protect.

Assign every critical function a second lane.

For each item on the sovereign inventory, ask: if the primary route for this freezes tomorrow, what moves instead? The answer doesn’t need to be perfect or immediate, it needs to exist before the freeze, not be improvised during one.

Shrink the blast radius deliberately.

Map which switches can affect which parts of your operation.

A payment processor restriction should not also be able to freeze your archive, your audience list, or your ability to deliver work.

Where you find switches with outsized reach - cross-platform dependencies, single sign-on, one payment account receiving everything - those are the points worth separating first.

Run the dry run.

Once a quarter, test one fallback. Not the whole system - one lane.

Can you actually export your subscriber list?

Can you actually access your work from a different device?

Can you actually invoice through the second payment corridor?

The fallback that’s never been tested is a plan, not infrastructure.

The Rule:

Rule #14: Don’t build to eliminate the switches. Build to limit what each switch can switch off. The platform is a lane. Make sure you own the road.
